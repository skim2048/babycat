26-07-26 작업 기록 — 프로토타입과 개정 SRS의 정합, SDD 착수 계획

이 문서는 26-07-26 시점의 저장소 전체 상태와, SDD 작성 및 프로토타입 정합 작업의 착수 순서·세부 계획을 기록한다.


1. 현재 상태
════════════════════════════════════════

(1) 코드 (프로토타입)

세 컨테이너와 별도의 대시보드로 구성되어 있다.

- gateway : FastAPI + SQLite. 인증·토큰, 이벤트 이력·클립 API, Engine 프록시를 맡는다.
- engine : 표준 라이브러리 HTTP 서버 + GStreamer + NanoLLM. 장면 분석, 클립 기록, 카메라 프로필, PTZ, SSE/MJPEG를 맡는다.
- media : MediaMTX. RTSP 수신과 HLS/WebRTC 재배포를 맡는다.
- web : Vue 3 대시보드. 별도 compose로 구동되는 참조용 프론트엔드다.

(2) SRS

여섯 구성요소 체계(Request router·Account manager·Source controller·Video streamer·Video analyzer·Event recorder)로 개정이 완료되었다. 미결 두 건(NFR-019의 주체·라이브 스트리밍 접근 통제 구조)이 docs/srs/README.md에 기록되어 있으며, 두 건 모두 설계 단계에서 결정하여 SRS로 환류하도록 예정되어 있다.

(3) SDD

전 장이 골격과 작성 지침 주석만 있는 상태다. 다만 HEAD 커밋에는 §3(65행)과 §4(341행)의 초안이 남아 있고, 작업 트리에서는 이 내용(총 386행)이 삭제되어 있으며 이 삭제는 커밋되지 않았다. 초안은 네 이름 체계(Gateway·Engine·Media·Storage)를 전제로 작성되었고 그 뒤 SRS가 여섯 구성요소 체계로 개정되었으므로, 전제가 무효화되어 비워둔 것으로 추정된다.

(4) memo.txt 재검증 (26-07-26, 현행 코드 기준)

memo.txt의 경로는 옛 구조(app/·api/·backup/web/) 기준이라 낡았다. 다섯 건을 현행 코드로 재검증한 결과는 다음과 같다.

1. 단일 진입점 : 전송 계층에서는 해소되었다. 커밋 82ca8b9로 Engine 포트가 비공개되고, Gateway가 /prompt·/ptz·/vlm/switch·/state·/stream을 프록시한다. 남은 것은 2번과 같은 설계 결정이다.
2. 스트림 접근 토큰 부재 : 유효하다. docs/srs/README.md의 접근 통제 미결과 동일한 사안이다.
3. 이벤트 이력 미기록 : 유효하다. Engine은 데이터베이스를 열지 않고, Gateway의 POST /events(gateway/main.py:463)를 호출하는 곳도 없다.
4. 차기 버전 기능 선구현 : 유효하다. devices API가 Gateway에 남아 있다(gateway/main.py:485-522).
5. 기본 프롬프트 불일치 : 유효하다. engine/main.py:91이 "What is the person doing? Answer in one sentence."를 사용한다.


2. 권고 착수 순서
════════════════════════════════════════

작업의 흐름이 SRS → SDD → 코드이고 미결 사항이 모두 설계 단계로 이관되어 있으므로, 다음 단계는 SDD 작성이며 SDD가 미결을 결정하는 도구가 된다.

1. 작업 트리 정리 — SDD §3·§4의 삭제 상태가 의도라면 커밋으로 확정한다. 아니라면 초안을 복원한 뒤 판단한다.
2. SDD §2·§3 작성 — 첫 산출물은 §3.2의 대응표, 곧 SRS 여섯 구성요소를 어떤 구현 단위로 실현하는가이다. Event recorder는 현재 기록(Engine 측)과 조회(Gateway 측)로 갈라져 있어, 이 대응을 정하면 memo 3번의 소속이 결정된다. §3.3 의존 관계를 그리면 NFR-019의 주체도 함께 정해진다.
3. 접근 통제 구조 결정 (SDD §6.2·§6.4) — 재생 요청이 Request router를 경유하는 구조와 별도 스트림 접근 토큰을 두는 구조 중 택일한다. 이 결정이 SRS §2.3 (6)/IF-003/FR-021·FR-023의 상충 해소, §4 프로필 용어 통일, memo 1·2번을 모두 좌우하는 상위 결정이다.
4. 결정을 SRS로 환류 — README의 지시대로 결정 내용을 SRS에 반영하고 README를 삭제한다.
5. 코드 반영 — memo 4·5번은 설계 결정을 기다릴 필요가 없으므로 아무 때나 처리할 수 있고, 3번은 2단계의 대응이 확정된 뒤 반영한다. 이때 memo.txt도 갱신하거나 역할을 다한 것으로 보고 정리한다.


3. 세부 계획
════════════════════════════════════════

단계 번호는 위 착수 순서를 따르며, 착수 순서에 없던 SDD 잔여 장 작성을 단계 6으로 덧붙인다.

단계 1 — 작업 트리 정리
----------------------------------------
- SDD §3·§4의 삭제가 의도된 상태인지 확정한다.
  - 의도라면 삭제를 커밋한다. HEAD 초안은 이력으로 남으므로 필요할 때 git show로 참조할 수 있다.
  - 의도가 아니라면 복원한 뒤 재작성 범위를 판단한다.
- 완료 기준 : git status가 깨끗하다.

단계 2 — SDD §2·§3 작성
----------------------------------------
- §2.3 설계 제약 : SRS §6.6의 CON-001~CON-004와 §6.7 메모리 제한에서 파생하여 작성한다.
- §2.1 설계 목표·§2.2 설계 원칙 : 저지연 재생, 16GB 메모리 내 안정 구동, 컴포넌트 교체 용이성 등 목표 사이의 우선순위를 밝힌다.
- §2.4 주요 설계 결정 : 단계 2~3에서 내리는 결정(구성요소 대응·접근 통제)을 이 절에 축적한다.
- §3.2 컴포넌트 구성 : 여섯 구성요소와 구현 단위의 대응표를 작성한다.
  - 자연 대응 : Request router·Account manager → gateway, Source controller·Video analyzer → engine, Video streamer → media.
  - 결정 사항 (a) : Event recorder의 실현 방식. 기록 주체(Engine이 Gateway API를 호출 / Engine이 데이터베이스에 직접 기록 / Gateway가 기록)와 조회 주체의 소속을 정한다. memo 3번이 여기서 해소되며, 결과가 §3.3의 의존 방향에 영향을 준다.
- §3.3 의존 관계 : 컴포넌트 사이의 호출 관계를 그린다.
  - 결정 사항 (b) : NFR-019의 주체. Video streamer의 기동 지연을 견뎌야 하는 쪽이 Source controller인지 Video analyzer인지, 아니면 양쪽 모두인지 확정한다. 결정 즉시 SRS NFR-019에 환류한다(미결 1 해소).
- §3.4 프로세스 및 스레드 구조·§3.5 기동 순서 : 현행 코드(depends_on: media → engine → gateway)를 참고하되, 관찰의 전사가 아니라 설계 근거로 재서술한다.
- 완료 기준 : 대응표와 의존 관계도가 확정되고, 결정 사항 (a)·(b)가 §2.4에 기록되어 있다.

단계 3 — 접근 통제 구조 결정 (SDD §6.2·§6.4 선행 작성)
----------------------------------------
- 두 안 중 택일한다.
  - 안 A : SRS §2.3 (6)의 구조. 재생 요청이 Request router를 경유하고 별도의 스트림 접근 토큰을 두지 않는다. 직접 전달되는 것은 WebRTC 미디어뿐이다.
  - 안 B : SRS §4 IF-003의 구조. Request router가 스트림 접속 정보(URL + 토큰)를 발급하고, Client app이 Video streamer에 직접 접속하며 Video streamer가 토큰을 검증한다.
- 판단 재료 :
  - WebRTC 미디어는 어느 안에서도 직접 전달되므로, 실질 차이는 시그널링과 HLS 경로에 있다.
  - 안 A는 HLS를 Request router가 프록시할 때의 부하와 지연을 감수한다.
  - 안 B는 폐기 지연(FR-023)을 감수하며, 허용 범위를 정해야 한다.
  - MediaMTX의 인증 기능이 안 B의 토큰 검증을 지원하는지 확인해야 한다. 현행 config/mediamtx.yml의 설정을 조사한다.
- 결정 후 SRS 환류 대상 : §2.3 (6) 또는 §4 IF-003·§4.1 통합 표·FR-021·FR-023 중 한쪽을 다른 쪽에 맞춘다(미결 2 해소).
- 완료 기준 : 택일과 근거가 SDD §2.4에 기록되어 있다.

단계 4 — SRS 환류와 README 삭제
----------------------------------------
- 단계 2~3의 결정을 SRS 해당 조항에 반영한다.
- §4의 "카메라 프로필" 다섯 곳(/camera 엔드포인트 두 곳·IF-002 두 곳·IF-004 한 곳)을 "비디오 소스 프로필"로 통일한다.
- docs/srs/README.md를 삭제한다.
- 완료 기준 : SRS 안에서 §2와 어긋나는 서술이 없고, README가 삭제되어 있다.

단계 5 — 코드 반영과 memo.txt 정리
----------------------------------------
- 설계 결정이 필요 없는 항목(즉시 가능) :
  - memo 5번 : engine/main.py:91의 기본 프롬프트를 "Describe the scene."으로 교체한다(FR-026).
  - memo 4번 : devices API(gateway/main.py:485-522)와 FCM 잔재(docker-compose.yml의 주석 설정)를 제거할지 비활성으로 둘지 정하고 처리한다.
- 설계 확정 후 반영하는 항목 :
  - memo 3번 : 단계 2의 결정 사항 (a)에 따라 이벤트 이력 기록 경로를 구현한다.
  - memo 1·2번 : 단계 3의 결정에 따라 스트림 접근 통제를 구현한다.
- memo.txt는 다섯 건이 모두 해소된 시점에 삭제하거나, 남은 항목만으로 갱신한다.
- 완료 기준 : SRS·SDD·코드 사이에 알려진 불일치가 없다.

단계 6 — SDD 잔여 장 작성 (단계 2~3 이후 계속)

4. 결정 확정 기록 (26-07-26 세션 후반)
════════════════════════════════════════

세부 계획의 단계 2~4에 해당하는 설계 결정이 모두 확정되어 SRS에 반영되었다.

(1) 컨테이너 체제 : 여섯 컨테이너. 이름은 구성요소 마지막 단어를 소문자로 쓴다
    (router·manager·controller·streamer·analyzer·recorder). NFR-020은 문구
    그대로 성립하므로 환류하지 않았다.
(2) Event recorder 실현 : recorder 단독. 클립·사이드카·이벤트 DB를 단독 소유하며,
    이벤트 이력 기록 공백(memo 3번)이 이로써 해소된다. 공유 SQLite 문제는 소멸.
(3) NFR-019 주체 : "Video streamer에 접속하는 컴포넌트"로 일반화. 스트림 접속
    재시도는 신설한 FR-046이 규정한다(§7.5).
(4) 그림 2-2 : Video streamer ↔ Event recorder 간선 추가(RTSP이므로 양방향).
    §2.3 (4)에 Event recorder의 사전 구간 보관 단계 추가. 버퍼는 분석 시작에
    연동한다(기동 시 무조건 시작 아님).
(5) 라이브 스트리밍 접근 통제 : 단일 진입점(안 A). HLS·WebRTC 시그널링은
    Request router 경유, WebRTC 미디어만 직접. 별도 스트림 접근 토큰 없음.
    FR-023 삭제(번호 불재사용), FR-021·IF-003·§4.1 표·§4.5 포트 표 개정.
    외부 공개 포트는 8000/tcp, 8890/udp 둘뿐이다. 프로필 용어 통일 완료,
    SRS README 삭제 완료.
(6) 세그먼트 인코딩 : NVENC(하드웨어). 세그먼트 기록기를 GStreamer
    nvv4l2h264enc로 재작성한다. recorder는 하드웨어 결합 컨테이너가 되며
    §3.4에 Jetson 실기 개발 대상으로 추가되었다. §3.1의 nvenc 확인 요구는
    근거를 회복하여 유지.
(7) 하드웨어 상태 측정 : Event recorder 소관. §2.2 역할 서술에 반영.
    근거는 가용성 비대칭(analyzer 재시작 중에도 관측 유지)과 관측 데이터
    친족성(디스크·저장 상태와 동거).
