# 실기 테스트 시나리오 (Test Scenarios)

작성 및 검토: @claude, @skim

본 문서는 테스트 코드로 검증할 수 없는 항목을 실기에서 수동으로 검증하기 위한 시나리오 모음이다. 실기 하드웨어(Jetson, 하드웨어 가속기), 컨테이너 오케스트레이션, 실시간 스트림, 외부 장비(RTSP 카메라), 브라우저 상호작용, 시간 경과에 의존하는 동작이 대상이며, 신규·수정 기능과 기존 기능을 모두 포함한다.

- 대상은 두 가지이다: 메인 프로젝트 `babycat`(시나리오 `M-xx`)과 서브프로젝트 `./web`(시나리오 `W-xx`).
- 각 시나리오는 **절차**와 **확인** 항목으로 구성한다. 별도 전제가 필요한 경우 **전제**를 먼저 적는다.
- 요구사항과의 연결이 필요한 곳에는 SRS 식별자(`FR-xxx` 등)를 병기한다.

## 준비물

- Jetson 실기(NVENC/NVDEC 확인: `ls /dev/v4l2-nvdec /dev/v4l2-nvenc`).
- RTSP(H.264) 비디오 소스: 실제 ONVIF PTZ 카메라 1대. PTZ 제외 항목은 대체 소스로도 가능하다.
- `.env`: `HOST_IP`·`JWT_SECRET`·`DEFAULT_USER`·`DEFAULT_PASS`를 설정한다.
- 클라이언트 2개 이상: 세션 대체 검증용으로 서로 다른 브라우저 또는 기기 2대.
- Jetson과 다른 네트워크 경로의 외부 노드 1대: WebRTC 외부 접속 검증용.
- 삭제·자동 정리 시나리오(M-44~M-47)는 데이터가 지워지므로 `data/` 백업 후 수행한다.

# 1부. 메인 프로젝트 `babycat`

## A. 빌드와 기동

**M-01 전체 이미지 빌드**
- 절차: 저장소 루트에서 `docker compose build`를 실행한다.
- 확인: 4개 이미지(`babycat-router`·`babycat-streamer`·`babycat-analyzer`·`babycat-recorder`)가 모두 빌드된다. 내부 포트 8080 통일이 반영된 최신 Dockerfile로 빌드되었는지 확인한다.

**M-02 필수 환경 변수 검증**
- 절차: `.env`에서 `HOST_IP`·`JWT_SECRET`·`DEFAULT_USER`·`DEFAULT_PASS` 중 하나를 비운 채 `docker compose up`을 시도한다.
- 확인: compose가 `required` 오류로 기동을 거부한다. 변수를 복원하면 기동된다.

**M-03 최초 기동과 VLM 준비**
- 전제: `data/models/` 캐시가 없는 상태.
- 절차: `docker compose up -d` 후 analyzer 로그와 `/state` SSE를 관찰한다.
- 확인: VLM 상태가 downloading/compiling을 거쳐 ready에 도달한다(모델당 수 분~수십 분). 초기 관리자 계정이 생성되고, VLM이 준비되기 전에도 로그인·프롬프트 저장 등 HTTP 요청이 동작한다.

**M-04 재기동 시 컴파일 캐시 재사용**
- 절차: M-03 완료 후 전체 스택을 재기동한다.
- 확인: analyzer 로그에 `MLC cache hit`가 남고 컴파일 없이 수 초~수 분 내 ready에 도달한다.

**M-05 내부 포트 비공개**
- 절차: 호스트에서 `docker ps`와 포트 스캔으로 공개 포트를 확인한다.
- 확인: 외부 공개 포트는 8000/tcp와 8189/udp뿐이다. streamer 동반 프로세스·analyzer·recorder의 8080은 호스트에서 접근되지 않고, router 컨테이너 내부에서는 세 호스트명 모두 8080으로 도달한다.

**M-06 재기동 상태 복원 (`FR-014`)**
- 전제: 스트리밍과 분석이 모두 진행 중.
- 절차: `docker compose restart`로 전체를 재기동한다.
- 확인: 재기동 후 개입 없이 스트리밍·분석·세그먼트 버퍼링이 모두 재개된다. 프롬프트와 이벤트 키워드도 유지된다. 스트리밍을 정지한 상태에서 재기동하면 정지 상태가 유지된다.

**M-07 MediaMTX 자식 프로세스 감시**
- 전제: 스트리밍 진행 중.
- 절차: streamer 컨테이너 내부에서 MediaMTX 프로세스를 강제 종료한다(`docker exec` + `kill`).
- 확인: 동반 프로세스가 MediaMTX를 재기동하고 적용 프로필을 재적용하여, 수 초~수십 초 내에 라이브 재생이 회복된다.

## B. 인증과 세션

**M-08 로그인 성공과 실패**
- 절차: 올바른 자격과 틀린 자격으로 각각 `/api/login`을 호출한다.
- 확인: 성공 시 액세스 토큰이 발급되고, 실패 시 401이 반환된다.

**M-09 로그인 시도 제한 (`FR-007`)**
- 절차: 틀린 비밀번호로 10회 연속 로그인을 시도한 뒤, 올바른 비밀번호로 로그인한다.
- 확인: 10회째부터 429와 `Retry-After` 헤더가 반환되고, 잠금 시간(30분) 동안은 올바른 비밀번호도 429로 거부된다.

**M-10 최초 로그인 비밀번호 변경 강제**
- 전제: 초기 계정으로 최초 로그인.
- 절차: 로그인 응답의 `must_change_password`를 확인하고 비밀번호를 변경한다.
- 확인: 최초 로그인 응답에만 `must_change_password: true`가 실리고, 변경 후 재로그인부터는 실리지 않는다.

**M-11 액세스 토큰 만료 (`FR-001`)**
- 절차: 로그인 유지 없이 로그인한 뒤 10분 경과 후 임의의 인증 API를 호출한다.
- 확인: 401이 반환된다.

**M-12 리프레시 토큰 회전 (`FR-002`, `FR-045`)**
- 절차: `remember_me: true`로 로그인하여 리프레시 토큰을 받고, `/api/refresh`를 호출한 뒤, 회전 전의 리프레시 토큰으로 다시 `/api/refresh`를 호출한다.
- 확인: 첫 호출은 새 토큰 쌍을 반환하고, 회전 전 토큰의 재사용은 401로 거부된다.

**M-13 로그아웃 즉시 폐기 (`FR-003`)**
- 절차: 로그인 후 `/api/logout`을 호출하고, 직전까지 유효했던 액세스 토큰으로 API를 호출한다.
- 확인: 만료 시각이 남아 있어도 401이 반환된다.

**M-14 비밀번호 변경 시 전체 세션 종료 (`FR-005`)**
- 전제: 동일 계정으로 SSE 수신과 WebRTC 재생 진행 중.
- 절차: `/api/change-password`로 비밀번호를 변경한다.
- 확인: 기존 액세스·리프레시 토큰이 모두 무효화되고, 진행 중이던 SSE·MJPEG 중계와 WebRTC 재생이 종료된다.

**M-15 세션 대체 (`FR-047`)**
- 전제: 브라우저 A에서 로그인하여 SSE·MJPEG·WebRTC 재생 진행 중.
- 절차: 브라우저 B에서 같은 계정으로 로그인한다.
- 확인: A의 API 호출이 401이 되고, 진행 중이던 SSE·MJPEG 중계가 수 초 내 끊기며, WebRTC 재생도 종료된다(라우터가 WHEP 세션을 DELETE). B의 세션은 정상 동작한다.

**M-16 라우터 재기동을 넘는 WHEP 종료**
- 전제: 브라우저 A에서 WebRTC 재생 진행 중.
- 절차: router 컨테이너만 재기동한 뒤, 브라우저 B에서 같은 계정으로 로그인한다.
- 확인: 재기동 전에 수립된 A의 WebRTC 재생이 종료된다(WHEP 레지스트리가 DB에 영속되어 재기동 후에도 정리 대상에 포함).

**M-17 쿼리 토큰 폴백과 접근 로그 마스킹**
- 절차: `?token=<JWT>`로 `/state` 또는 클립 재생을 호출한 뒤 router의 접근 로그를 확인한다.
- 확인: 헤더 없이 쿼리 토큰만으로 인증되며, 접근 로그에는 토큰 값이 `token=***`으로 마스킹되어 원문이 남지 않는다.

**M-18 CORS 정책**
- 절차: 사설망 origin(예: `http://192.168.x.x:5173`)과 외부 도메인 origin에서 각각 API를 호출한다.
- 확인: 사설망·localhost origin은 허용되고, 등록되지 않은 외부 도메인은 차단된다. `CORS_EXTRA_ORIGINS`에 추가한 도메인은 허용된다.

## C. 비디오 소스 프로필

**M-19 등록은 연결하지 않는다 (`FR-048`)**
- 절차: 스트리밍 정지 상태에서 `POST /camera`로 프로필을 등록한다.
- 확인: MediaMTX 소스가 변경되지 않고(카메라로 연결 시도 없음) PTZ도 구성되지 않는다. 저장만 수행된다.

**M-20 프로필 조회 마스킹 (`FR-013`)**
- 절차: `GET /camera`를 호출한다.
- 확인: 비밀번호 원문 대신 `password_set` 여부만 반환된다.

**M-21 부분 수정 병합**
- 절차: 비밀번호 필드를 비운 채 다른 필드만 수정하여 등록한다.
- 확인: 기존 비밀번호가 유지된 채 나머지 필드만 갱신된다.

**M-22 필수 필드 검증**
- 절차: `ip`/`username`/`password` 중 하나가 빠진 프로필을 등록한다.
- 확인: `ok: false`와 해당 필드의 오류 사유가 반환되고 기존 프로필은 보존된다.

**M-23 미적용 변경 표시**
- 전제: 스트리밍 진행 중.
- 절차: 프로필을 수정 등록한 뒤 상태를 조회한다.
- 확인: 등록 프로필과 적용 프로필이 달라 `profile_pending`이 참이 되고, 스트리밍 재시작 후 거짓으로 돌아온다.

## D. 라이브 스트리밍

**M-24 스트리밍 시작 (`FR-048`)**
- 절차: 프로필 등록 후 `/streaming/start`를 호출하고 HLS와 WebRTC로 각각 재생한다.
- 확인: 카메라 스트림이 연결되고 두 방식 모두 재생된다. 같은 요청을 반복해도 오류 없이 동일 상태가 유지된다(멱등).

**M-25 프로필 없는 시작 거부**
- 전제: 등록 프로필이 없는 초기 상태.
- 절차: `/streaming/start`를 호출한다.
- 확인: 등록 프로필이 없다는 실패 응답이 반환되고 연결 시도가 없다.

**M-26 재시작 겸용과 PTZ 홈 무효화**
- 전제: 스트리밍 진행 중, PTZ 홈 저장됨.
- 절차: 프로필을 수정 등록한 뒤 `/streaming/start`를 다시 호출한다.
- 확인: 새 프로필로 재연결된다. IP가 같으면 PTZ 홈이 유지되고, 다른 IP로 바꾸면 홈이 무효화된다.

**M-27 스트리밍 종료와 소스 해제 (`FR-049`)**
- 전제: 스트리밍과 분석이 모두 진행 중.
- 절차: `/streaming/stop`을 호출한 뒤 streamer 컨테이너 내부에서 MediaMTX API(`127.0.0.1:9997`)로 `live` 경로 설정을 조회한다.
- 확인: `source`가 `publisher`로 되돌아가 카메라 연결이 끊기고, 분석과 세그먼트 버퍼링도 함께 정지한다. 이후 새 이벤트가 발생하지 않는다.

**M-28 연쇄 정지의 실패 보고**
- 절차: recorder 컨테이너를 정지시킨 상태에서 `/streaming/stop`을 호출하고, recorder 복구 후 재요청한다.
- 확인: 첫 요청은 502와 함께 실패한 컴포넌트 이름을 반환하되 나머지 정지는 수행되어 있다. 재요청으로 전체 정지가 완성된다.

**M-29 분석 시작의 스트리밍 전제 (`FR-050`)**
- 절차: ① 스트리밍 정지 상태에서 `/analysis/start`를 호출한다. ② streamer 컨테이너를 정지시킨 상태에서 다시 호출한다.
- 확인: ①은 409(스트리밍 미활성), ②는 502(상태 확인 불가)로 구분되어 거부된다.

**M-30 스트림 수신 장애와 재연결**
- 전제: 스트리밍과 분석 진행 중.
- 절차: 카메라의 네트워크를 분리했다가 수 분 후 복구한다.
- 확인: 장애 동안 시스템이 종료되지 않고 재시도를 지속하며, 복구 후 라이브 재생과 분석이 개입 없이 재개된다.

**M-31 WebRTC 외부 노드 접속**
- 절차: Jetson과 다른 네트워크 경로의 외부 노드에서 WebRTC 재생을 시도한다.
- 확인: `.env`의 `HOST_IP`가 ICE 후보로 광고되어 미디어가 UDP 8189로 직접 수신된다. `HOST_IP`를 잘못 설정하면 시그널링은 성립해도 미디어 수신이 실패함을 함께 확인한다.

**M-32 스트리밍 중계 인증**
- 절차: 토큰 없이 `/live/hls/index.m3u8`과 `/live/whep`을 호출한다.
- 확인: 둘 다 401로 거부된다. 유효 토큰으로는 중계된다.

## E. 비디오 분석과 이벤트

**M-33 프롬프트·키워드 설정과 지속**
- 절차: `/prompt`로 프롬프트와 키워드를 설정하고 analyzer 컨테이너를 재기동한다.
- 확인: 설정이 즉시 적용되고(다음 추론부터 반영) 재기동 후에도 유지된다.

**M-34 분석 시작과 추론 주기**
- 전제: 스트리밍 진행 중, VLM ready.
- 절차: `/analysis/start`를 호출하고 SSE와 analyzer 로그를 관찰한다.
- 확인: 파이프라인이 기동되어 약 1 fps로 프레임이 추출되고, 추론 결과와 소요 시간이 SSE로 갱신된다.

**M-35 이벤트 감지와 클립 생성 (`FR-026`~)**
- 절차: 이벤트 키워드에 해당하는 장면을 카메라 앞에서 연출한다.
- 확인: 이벤트가 이력에 기록되고, 사전 구간을 포함한 클립(mp4)과 메타데이터 사이드카(json)가 생성된다. 클립 파일명이 이력의 `clip_name`과 일치한다.

**M-36 이벤트 쿨다운 (`FR-030`)**
- 절차: 이벤트 장면을 30초 이내에 연속으로 연출한다.
- 확인: 첫 이벤트만 클립을 발행하고 쿨다운 내 후속 이벤트는 클립을 만들지 않는다. recorder를 재기동해도 쿨다운 기준 시각이 유지된다.

**M-37 정지 후 이벤트 부재**
- 절차: 추론이 진행 중인 시점에 `/analysis/stop`을 호출한다.
