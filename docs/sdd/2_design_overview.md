# 2. 설계 개요 (Design Overview)

## 2.1 설계 목표 (Design Goals)

이 설계는 다음을 우선순위 순으로 추구한다. 목표가 서로 충돌할 때는 앞선 목표를 지키는 쪽으로 결정한다.

1. **무인 안정 구동** — 16GB 통합 메모리 안에서 관리자 개입 없이 상시 동작한다(SRS `NFR-017`·`NFR-022`). 어떤 결정도 이 목표를 해치면서 채택되지 않는다.
2. **저지연 라이브 재생** — 현장 확인의 수단인 WebRTC 재생 경로에서 불필요한 홉을 제거한다(SRS `FR-021`).
3. **관측 가능성** — 무인으로 도는 시스템의 상태를 언제든 실시간으로 확인할 수 있게 한다(SRS `FR-042`·`FR-043`). 특히 시스템이 힘들어하는 순간에 관측이 함께 꺼지지 않아야 한다.
4. **컴포넌트 독립 빌드·교체** — 각 역할을 독립적으로 빌드·교체할 수 있게 한다(SRS `NFR-020`).

충돌의 예를 들면, 저지연(2)과 접근 통제는 재생 경로에서 부딪히며 그 해소가 §2.4 (2)의 결정이다. 안정 구동(1)과 클립 경계 정밀도는 인코딩 방식에서 부딪히며 그 해소가 §2.4 (3)의 결정이다.

## 2.2 설계 원칙 (Design Principles)

문서 전체의 개별 결정은 다음 원칙에서 파생된다.

- **단일 진입점** — 모든 외부 요청은 ***Request router***를 거친다. 예외는 WebRTC 미디어 하나뿐이며, 예외를 둘 때는 §2.4에 결정으로 기록한다.
- **데이터 단독 소유** — 모든 영속 데이터는 정확히 하나의 컴포넌트가 소유한다. 다른 컴포넌트는 소유자의 인터페이스를 거쳐 접근하며, 파일이나 데이터베이스를 직접 공유하지 않는다.
- **하드웨어 의존 격리** — Jetson 하드웨어와 플랫폼 라이브러리 의존은 그것을 실제로 요구하는 컴포넌트(***Video analyzer***·***Event recorder***) 안에 가둔다.
- **재시작 비용의 비대칭 존중** — 복구는 컨테이너 재시작 정책에 맡기므로(SRS `NFR-018`), 값싼 고장이 비싼 재시작을 부르지 않도록 재시작 비용이 다른 책임을 한 컨테이너에 두지 않는다.
- **신뢰 경계 최소화** — 인증은 ***Request router*** 한곳에서 수행한다. ***Request router***를 통과한 요청은 정당한 것으로 간주되므로 내부 호출은 재검증하지 않는다(SRS §2.3 (6)).
- **기다림의 일원화** — 다른 컴포넌트의 준비를 통지로 알리지 않는다. 필요한 쪽이 간격을 늘려가며 재시도하여 스스로 연결을 확보한다(SRS `FR-015`·`FR-046`).

## 2.3 설계 제약 (Design Constraints)

설계자가 선택할 수 없는 조건과, 각 조건이 설계를 좁히는 방향은 다음과 같다.

- `CON-001` (NanoLLM) — ***Video analyzer***의 베이스 이미지가 jetson-containers 계열로 고정되고, 해당 컴포넌트는 Jetson 실기에서만 개발·검증할 수 있다(SRS §3.4).
- `CON-002` (H.264 한정) — 파이프라인에 코덱 추상화 계층을 두지 않는다. 디코딩은 `nvv4l2decoder` 단일 경로다.
- `CON-003` (Docker Compose) — 배포 단위가 컨테이너로 고정된다. Compose의 기동 순서 표현은 프로세스 시작까지만 보장하므로, 준비 대기는 §3.5의 재시도 설계로 해결해야 한다.
- `CON-004` (SQLite) — 데이터베이스가 파일 단위로 존재하므로, 데이터 단독 소유 원칙과 결합하여 컴포넌트마다 별도의 데이터베이스 파일을 두는 배치(§5)로 이어진다.
- SRS §6.7 (16GB·단일 모델 적재) — VLM 모델 전환은 반환 후 재적재로 직렬화되며(`NFR-023`), 상주 프로세스의 메모리 여유를 상시 관리해야 한다.
- `NFR-013` (HMAC-SHA256 대칭키) — 서명 비밀키를 아는 컴포넌트를 최소로 유지해야 하므로, 키는 토큰을 발급하는 ***Account manager***와 검증하는 ***Request router***에만 주입한다.

## 2.4 주요 설계 결정 (Key Design Decisions)

대안이 있었던 결정만 기록한다. 각 항목은 결정, 검토한 대안, 선택 근거, 감수하는 손실의 순서다.

### (1) 컴포넌트와 컨테이너의 1:1 대응

- **결정**: SRS §2.2의 여섯 구성요소를 각각 독립된 컨테이너로 실현한다. 컨테이너 이름은 구성요소 이름의 마지막 단어를 소문자로 쓴다(`router`·`manager`·`controller`·`streamer`·`analyzer`·`recorder`).
- **대안**: 제어 계열(***Request router***·***Account manager***·***Source controller***)을 한 컨테이너로 묶는 3~4개 구성.
- **근거**: SRS와 배포가 1:1로 대응하여 요구사항 추적(§9)이 기계적으로 성립한다. 데이터 단독 소유가 자연히 성립하여 두 프로세스가 한 SQLite 파일을 쓰는 문제가 생기지 않는다. 신뢰할 수 없는 외부 장비를 상대로 대기·재시도하는 ***Source controller***(`FR-015`·`FR-020`)를 항상 즉시 응답해야 하는 진입점과 격리한다. 하드웨어 무관 컴포넌트 셋을 일반 PC에서 개발할 수 있게 되어 SRS §3.4의 취지가 실현된다.
- **손실**: Compose 서비스·이미지·로그 스트림이 늘어난다. 한 프로세스 안에서 공짜였던 신호와 상태 공유(카메라 준비 신호, 모니터링 스냅숏)를 컨테이너 간 인터페이스로 재설계해야 한다 — 각각 (5)와 §6.4에서 해소한다.

### (2) 라이브 스트리밍의 단일 진입점 유지

- **결정**: 재생 요청·HLS 비디오·WebRTC 시그널링은 ***Request router***를 경유하고, WebRTC 미디어만 직접 전달한다(SRS `FR-021`). 별도의 스트림 접근 토큰을 두지 않으며 ***Video streamer***는 자체 접근 통제를 수행하지 않는다.
- **대안**: ***Client app***이 ***Video streamer***에 직접 접속하고, ***Video streamer***가 MediaMTX의 HTTP 인증 콜백으로 검증을 ***Account manager***에게 위임하는 구조. (MediaMTX의 자체 JWT 검증은 JWKS 비대칭키를 요구하여 `NFR-013`과 충돌하므로 처음부터 제외하였다.)
- **근거**: 인증과 폐기가 ***Request router*** 한곳에 남고, 외부 공개 포트가 8000/tcp·8890/udp 둘로 준다. WebRTC 미디어는 어느 안에서도 직접 흐르므로 저지연 요구의 충족은 같고, HLS는 프로토콜 자체가 수 초의 지연을 지녀 프록시 한 홉이 체감을 바꾸지 않는다.
- **손실**: ***Request router***가 HLS 미디어 경로에 들어간다(소수 운영자 전제로 감수, SRS §5.2). WHEP 세션 중계(Location 재작성 포함)를 구현해야 한다. 다중 세션 확장 시 이 경로가 먼저 한계에 닿으므로 차기 버전에서 재검토한다.

### (3) 세그먼트 인코딩의 NVENC 전환

- **결정**: ***Event recorder***의 세그먼트 기록기를 하드웨어 인코더(NVENC, `nvv4l2h264enc`) 기반 GStreamer 파이프라인으로 구현한다.
- **대안**: ① 프로토타입의 `libx264` 소프트웨어 인코딩 유지 — 분석 중 상시 CPU 코어 수 개 몫을 소모하여 VLM과 경합한다. ② 재인코딩 제거(`-c copy` 분할) — CPU 비용은 사라지나 클립 경계가 카메라 키프레임 간격(수 초)으로 거칠어진다.
- **근거**: 1초 키프레임 강제로 클립 경계 정밀도를 유지하면서 상시 CPU 비용을 제거하여, 설계 목표 1(안정 구동)과 클립 품질을 양립시킨다.
- **손실**: ***Event recorder***가 하드웨어 결합 컨테이너가 되어 Jetson 실기에서만 개발할 수 있다(SRS §3.4 반영 완료). NVDEC 디코드 세션을 ***Video analyzer***와 나눠 쓴다(§7.4).

### (4) 사전 버퍼의 분석 연동

- **결정**: ***Event recorder***의 세그먼트 버퍼는 분석 시작 요청과 함께 시작한다(SRS §2.3 (4)). 기동만으로는 시작하지 않는다.
- **대안**: 프로토타입처럼 기동과 동시에 무조건 시작.
- **근거**: 이벤트 판정은 분석 중에만 일어나므로, 분석 정지 중의 버퍼 기록은 소비될 수 없는 산출물에 자원을 지불하는 일이다.
- **손실**: 분석 시작 직후에는 축적된 사전 구간이 없어, 그 시점에 발생한 이벤트의 클립은 사전 구간이 짧다.

### (5) 준비 통지의 제거

- **결정**: ***Video analyzer***와 ***Event recorder***는 재배포 스트림 접속을 스스로 재시도하여 확보한다(SRS `FR-046`). ***Source controller***가 소스 활성화를 두 컴포넌트에게 통지하는 경로는 두지 않는다.
- **대안**: 프로토타입의 프로세스 내부 신호(`camera_ready`)를 컨테이너 간 통지 API로 외부화.
- **근거**: 스트림 접속 실패의 원인(***Video streamer*** 미기동, 소스 미설정, 카메라 연결 지연)이 무엇이든 대응은 재시도 하나로 같으므로 원인 구별이 필요 없다. 결합이 줄고, ***Source controller***가 잠시 내려가도 나머지 컴포넌트의 기동이 막히지 않는다.
- **손실**: 실패 원인이 통지로 구별되지 않으므로 진단은 각 컴포넌트의 로그에 맡긴다.

### (6) 하드웨어 상태 측정의 ***Event recorder*** 배정

- **결정**: 온도·메모리 등 하드웨어 상태(`FR-043`)의 측정을 ***Event recorder***가 수행한다(SRS §2.2 반영 완료).
- **대안**: ***Video analyzer***에 동거(프로토타입 구조).
- **근거**: 관측이 가장 필요한 순간 — 메모리 압박, 모델 재적재, 파이프라인 재시작 — 에 ***Video analyzer***는 침묵하거나 재시작 중이다. 재시작이 싸고 항상 떠 있는 컴포넌트에 관측을 두어야 그 순간에도 상태가 보인다. 측정의 실체는 /proc·/sys 파일 읽기라서 어느 컨테이너에서든 비용이 같고, ***Event recorder***는 이미 디스크·저장 상태라는 인접 관측 데이터를 소유한다.
- **손실**: 없음에 가깝다. 측정 모듈의 이동뿐이다.

## 2.5 기술 스택 선정 (Technology Stack Selection)

SRS가 이미 지정한 항목(NanoLLM·SQLite·MediaMTX·Docker Compose)은 §2.3의 제약이므로 여기서 반복하지 않는다. 컴포넌트별 선정은 다음과 같다.

|컴포넌트|언어·프레임워크|선정 근거|
|---|---|---|
|`router`·`manager`·`controller`|Python 3 + FastAPI/uvicorn|SRS §4.4가 ***Request router***용으로 지정한 프레임워크와 같은 계열로 통일하여 학습·유지 비용을 줄인다. 프로토타입 코드 자산을 재사용한다.|
|`analyzer`|Python 3 + 표준 라이브러리 HTTP 서버 + GStreamer(PyGObject)|NanoLLM 베이스 이미지에 대한 의존 추가를 최소화한다. HTTP 표면이 좁아 프레임워크가 필요하지 않다.|
|`recorder`|Python 3 + FastAPI/uvicorn + GStreamer(PyGObject) + ffmpeg|세그먼트 기록은 GStreamer(NVENC), 무재인코딩 결합과 직접 녹화 폴백은 ffmpeg(`-c copy`)가 맡는다. 클립·이력 API는 제어 계열과 같은 FastAPI로 통일한다.|
|`streamer`|MediaMTX|기성품을 설정만으로 사용한다(`CON` 외 선택 없음).|

***Client app***(참조 구현 `web/`, Vue 3)은 `Babycat`의 범위 밖이므로 선정 대상이 아니다.
