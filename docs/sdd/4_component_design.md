# 4. 컴포넌트 설계 (Component Design)

각 절은 책임, 내부 구조, 노출하는 인터페이스, 내부 상태의 순서로 서술한다. 컴포넌트와 컨테이너는 1:1이므로(§2.4 (1)) 절 제목에 컨테이너 이름을 병기한다. 인터페이스의 경로 수준 상세는 §6에서 정한다.

## 4.1 Request router (`router`)

### 책임

단일 외부 진입점이다. 계정의 인증·관리(자격증명 검증, 토큰의 발급·회전·폐기, 비밀번호 변경, 로그인 시도 제한), 요청의 컴포넌트별 라우팅, HLS·WebRTC 시그널링의 중계, 모니터링 스트림의 합성을 맡는다. 계정 데이터베이스를 단독 소유한다.

### 내부 구조

|모듈|책임|
|---|---|
|`main`|외부 경로의 정의와 컴포넌트별 전달|
|`auth`|자격증명 검증, 토큰의 발급·회전·폐기, 로그인 시도 제한, 요청 인증|
|`database`|계정 데이터베이스 연결과 스키마 초기화|
|`relay`|HLS·WHEP 중계와 SSE·MJPEG 스트림 전달|
|`monitor`|컴포넌트별 상태의 수집과 단일 모니터링 스트림 합성(§6.4)|

비밀번호는 솔트와 함께 PBKDF2-HMAC-SHA256을 100,000회 적용하여 저장한다(`NFR-012`). 토큰은 HMAC-SHA256으로 서명하며 서명 비밀키는 외부에서 주입받는다(`NFR-013`). 리프레시 토큰은 원문을 저장하지 않고 해시로만 저장하며, 갱신 시 회전한다(`FR-002`·`FR-045`).

요청 인증은 두 단계다. 서명과 만료는 공유 비밀키로 자체 검증하고(`FR-001`), 폐기 여부는 토큰의 세대(epoch) 클레임을 계정 데이터베이스의 현재 세대와 대조하여 확인한다(§6.2). 발급과 검증이 한 프로세스에 있으므로 이 대조는 자기 데이터베이스 읽기 한 번이다. 로그인 시도 제한(`FR-007`)의 실패 계수와 차단 만료 시각은 데이터베이스에 저장한다 — 프로세스 메모리에 두면 컨테이너 재시작으로 초기화되어 차단을 회피할 수 있기 때문이다.

헤더를 설정할 수 없는 클라이언트 기능(HLS 재생, SSE, MJPEG)을 위해 `?token=` 쿼리 파라미터를 허용한다(SRS §4.1).

### 노출하는 인터페이스

***Client app***에게 HTTP를 제공한다(§6.1). 내부 컴포넌트에게 전달할 때 인증 정보를 벗겨낸다 — ***Request router***를 통과한 요청은 정당한 것으로 간주되므로 내부에서 재검증하지 않는다(§2.2). 상류 컴포넌트가 응답하지 않거나 서버 오류를 돌려주면 502로 정규화하여 응답한다(§6.5).

### 내부 상태

계정 데이터베이스(§5.2)가 전부다. 그 외의 상태를 갖지 않으므로 재시작으로 잃는 것이 없다.

## 4.2 Video streamer (`streamer`)

### 책임

***Video source***를 상대하는 유일한 컴포넌트다. 비디오 소스 프로필의 등록·조회·수정(`FR-009`~`FR-013`), RTSP 스트림의 수신과 내부 재배포, HLS/WebRTC 송출, PTZ 제어(`FR-016`~`FR-020`)를 맡는다. 프로필 파일을 단독 소유하며, 소유한 설정의 소비자가 자기 자신이다.

### 내부 구조

컨테이너는 두 프로세스로 구성된다(§3.4).

- **MediaMTX(자식 프로세스)** — 미디어의 수신·재배포·송출 전부를 맡는 기성품. `Babycat`이 작성하는 것은 설정뿐이다.
- **동반 프로세스(부모)** — MediaMTX의 감독과, 미디어 이외의 모든 책임을 맡는 우리 코드.

|동반 프로세스 모듈|책임|
|---|---|
|`main`|내부 경로의 정의, MediaMTX 자식 프로세스의 기동·감독·신호 전달|
|`camera`|프로필의 정규화·영속화와 MediaMTX 소스 설정(제어 API, localhost)|
|`ptz`|ONVIF SOAP 명령(연속 이동/정지/절대 이동/상태 조회)과 홈 위치|

프로필 적용은 localhost의 MediaMTX 제어 API에 RTSP 소스 URL을 설정하는 것이다. 기동 직후에는 MediaMTX가 아직 준비되지 않았을 수 있으므로 간격을 늘려가며 재시도한다(`FR-015`). 같은 컨테이너 안의 일이므로, 재시작으로 소스 설정이 소실되는 상황은 동반 프로세스의 기동 절차가 자연히 복구하며, 외부의 감시·재적용 절차가 필요 없다(§2.4 (1)).

***Video source***가 ONVIF를 지원하지 않거나 접근을 거부하면 PTZ 요청은 오류 없이 무시된다(`FR-020`). PTZ 현재 위치는 폴링 스레드가 주기적으로 조회하여 유지하고, 모니터링 합성(§6.4)에 상태로 제공한다.

MediaMTX 설정의 원칙은 다음과 같다.

- 소스는 설정 파일에 고정하지 않는다. 자격증명이 프로필에 있으므로 설정 파일에 담으면 형상 관리 제외 원칙(SRS §3.6)에 어긋난다. 동반 프로세스가 런타임에 설정한다.
- 자체 인증을 두지 않는다(§2.4 (2)). 재생 요청의 인증은 ***Request router***가 끝냈고, 컨테이너 네트워크 내부는 신뢰 경계 안이다. 외부에 열리는 것은 WebRTC 미디어(8890/udp)뿐이며, 이 경로는 시그널링에서 교환된 ICE 자격 없이는 수립되지 않는다.
- WebRTC는 외부 도달 가능한 IP를 ICE 후보로 광고해야 하므로, 호스트 IP를 환경 변수로 주입받는다(§8.3).

### 노출하는 인터페이스

***Request router***에게 HTTP(프로필·PTZ·활성화·상태)와 중계 상류(HLS·WHEP)를 제공한다(§6.3). ***Video analyzer***·***Event recorder***에게 재배포 스트림(RTSP)을 제공하고, ***Client app***에게 WebRTC 미디어를 직접 송출한다. ***Video source***에는 RTSP·ONVIF로 접속하는 클라이언트다.

### 내부 상태

프로필 파일(홈 위치 포함, §5.4)과 폴링으로 유지되는 PTZ 현재 위치, 그리고 재배포 중인 스트림이다. 프로필은 영속이고 나머지는 재시작 시 기동 절차와 소비자들의 재접속(`FR-046`)으로 회복된다.

## 4.3 Video analyzer (`analyzer`)

### 책임

재배포 스트림에서 프레임을 추출하여 VLM으로 장면 설명을 생성하고(`FR-028`), 이벤트 키워드와 대조하여 이벤트를 판정하며(`FR-029`), 판정 시 ***Event recorder***에게 기록을 통지한다. 프롬프트·이벤트 키워드 설정(`FR-026`·`FR-027`)과 VLM 모델 전환(`FR-032`)도 맡는다. 하드웨어 가속기와 Jetson 플랫폼 라이브러리에 의존하는 가장 무거운 컴포넌트이므로, 이 절만 모듈 수준까지 서술한다.

인증, 클립·이력의 저장과 조회, 하드웨어 상태 측정은 ***Video analyzer***의 책임이 아니다.

### 내부 구조

|모듈|책임|
|---|---|
|`main`|기동 절차, GStreamer 파이프라인, 추론 워커, 이벤트 판정|
|`state`|공유 런타임 상태와 SSE 구독 관리|
|`server`|HTTP 서버(설정·상태·MJPEG)|
|`holder`·`vlm_worker`|VLM 자식 프로세스의 수명과 추론 실행|
|`pipeline_lifecycle`|파이프라인 시작·재시작 조건의 판정|
|`notify`|***Event recorder***로의 이벤트 통지|

파이프라인은 `rtspsrc → rtph264depay → h264parse → nvv4l2decoder → nvvidconv → videorate → appsink`로 구성한다. `videorate`가 프레임을 목표 주기로 정규화하므로 카메라의 원 프레임레이트와 무관하게 추출 간격이 일정하다. 추출 프레임은 링 버퍼에 쌓이고, 추론 워커가 최신 프레임 묶음을 VLM 자식 프로세스에 전달한다. 추론이 수 초 걸리는 동안에도 파이프라인과 HTTP 서버는 막히지 않는다(§3.4).

이벤트 판정은 생성 텍스트에 대한 대소문자 무시 부분 일치다(`FR-029`). 판정 시 매칭 키워드·장면 설명·판정 시각을 담아 ***Event recorder***에 통지하고, 통지의 성공 여부와 무관하게 다음 추론을 계속한다 — 기록의 완결은 ***Event recorder***의 책임이다.

모델 전환(`FR-032`)은 자식 프로세스를 종료하여 메모리를 반환한 뒤 새 모델을 적재하는 직렬 절차다(`NFR-023`). 전환 중 분석은 중단되며 그 상태가 모니터링에 드러난다.

### 노출하는 인터페이스

***Request router***에게 HTTP(설정·시작·상태 SSE·MJPEG)를 제공한다(§6.3). ***Event recorder***의 통지 경로에 대해서는 클라이언트다.

### 내부 상태

프롬프트·이벤트 키워드·분석 활성 여부를 상태 파일에 영속한다(§5.4). 재기동 시 이를 읽어 직전 상태를 복원한다(`FR-014`). 링 버퍼와 추론 결과는 휘발 상태다.

## 4.4 Event recorder (`recorder`)

### 책임

이벤트 구간 클립의 기록과 발생 이력의 저장(`FR-030`·`FR-031`), 클립·이력의 조회·재생·삭제 API(`FR-034`~`FR-041`), 저장 공간 자동 관리(`FR-033`), 하드웨어 상태 측정(`FR-043`, §2.4 (6))을 맡는다. 이벤트 데이터베이스와 클립 파일을 단독 소유한다.

### 내부 구조

|모듈|책임|
|---|---|
|`main`|내부 경로의 정의, 이벤트 통지 수신|
|`segments`|NVENC 세그먼트 기록 파이프라인과 보존 관리|
|`finalize`|이벤트 구간 세그먼트의 무재인코딩 결합, 사이드카 생성, 직접 녹화 폴백|
|`clips`|클립 목록·재생(Range)·삭제와 용량 관리|
|`events_db`|이벤트 데이터베이스 연결과 이력 기록·조회|
|`hardware`|/proc·/sys 기반 하드웨어 상태 측정|

세그먼트 기록은 GStreamer 파이프라인 `rtspsrc → rtph264depay → h264parse → nvv4l2decoder → nvvidconv → nvv4l2h264enc → h264parse → splitmuxsink`로 구현한다(§2.4 (3)). 인코더에 1초 키프레임을 강제하여 1초 단위 세그먼트를 tmpfs에 남기고, 보존 시간을 지난 세그먼트는 즉시 삭제한다. 이 파이프라인은 분석 시작 요청과 함께 기동하고(§2.4 (4)), 분석 활성 여부를 영속하여 재기동 시 복원한다(`FR-014`).

이벤트 통지를 받으면 이벤트 전후 구간의 세그먼트를 골라 재인코딩 없이 결합하여 mp4를 만들고, 매칭 키워드·장면 설명·발생 시각을 담은 사이드카 json을 같은 이름으로 저장하며(`FR-030`), 같은 절차 안에서 발생 이력을 데이터베이스에 기록한다(`FR-031`). 클립·사이드카·이력이 한 컴포넌트의 한 절차에서 만들어지므로 짝이 어긋날 여지가 최소화된다. 클립 창의 기준점은 판정 시각이 아니라 통지에 실린 프레임 캡처 시각이다(§7.2). 세그먼트의 실제 길이는 목표(1초)와 다를 수 있으므로 — 인코더의 키프레임 간격이 프레임 수 기준이라 카메라 프레임레이트에 따라 늘어난다 — 창에 걸친 세그먼트의 선별은 고정 길이 가정 없이 각 세그먼트의 시작 시각과 다음 세그먼트의 시작 시각으로 실측 산정한다. 세그먼트 결합이 불가능하면(버퍼 공백 등) 재배포 스트림을 이벤트 시점부터 무재인코딩으로 직접 녹화하는 폴백을 쓴다. 동일 이벤트의 연속 판정은 쿨다운으로 묶음 처리한다(`FR-030`).

가용 저장 공간이 임계 이하로 떨어지면 가장 오래된 클립·사이드카·이력부터 삭제하여 공간을 확보하고, 삭제 사실을 로그에 남긴다(`FR-033`·`NFR-010`).

### 노출하는 인터페이스

***Request router***에게 HTTP(클립·이력·상태)를, ***Video analyzer***에게 이벤트 통지 수신 경로를 제공한다(§6.3).

### 내부 상태

이벤트 데이터베이스(§5.2), 클립·사이드카 파일(§5.3), 분석 활성 플래그, tmpfs의 세그먼트 버퍼를 가진다. 세그먼트 버퍼는 휘발이어도 무방하다 — 재시작 직후의 사전 구간 공백은 §2.4 (4)가 이미 감수한 손실과 같은 성격이다.
