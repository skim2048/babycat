# 7. 동작 설계 (Behavioral Design)

## 7.1 주요 시나리오 흐름 (Primary Scenario Flows)

각 시나리오의 메시지 흐름 — 단계, 간선, 전송 형태 — 은 §6.6이 그림과 함께 정의한다. 이 절은 형태만으로 드러나지 않는 동작적 성질을 보탠다.

### (1) 스트리밍 시작과 종료 (§6.6 (3))

시작은 그 시점의 등록 프로필을 적용 프로필로 승격하는 스냅숏이다 — 이후의 등록은 접속에 영향을 주지 않으며, 등록 프로필과 적용 프로필이 다른 상태는 모니터링에 드러난다(§6.4 (4)). 종료의 연쇄 정지는 병렬 전달이므로 부분 실패가 가능하며, 시작과 마찬가지로 재요청이 수복 수단이다(§6.1). 장애로 인한 스트림 단절은 종료가 아니다 — 소비자들은 재시도로 대기하고(`FR-046`), 소스 연결은 MediaMTX가 적용 프로필로 유지한다. 재시도 간격은 점진적으로 늘어나므로(§7.5), 복구된 스트림에 분석이 다시 붙기까지 최대 재시도 간격(약 1분)이 걸릴 수 있다 — 이 지연은 스트리밍이 분석을 직접 건드리는 결합을 두지 않는 대가로 수용한다.

### (2) 분석 시작과 종료 (§6.6 (5))

두 컴포넌트는 서로의 완료를 기다리지 않는다. 시작은 라이브 스트리밍이 진행 중일 때만 수락되므로(`FR-050`) 재배포는 이미 흐르는 상태이며, 접속이 일시적으로 늦으면 재시도로 대기한다(§2.4 (5)). ***Request router***의 응답은 각 컴포넌트가 요청을 접수했는지만 뜻한다. `analyzer`와 `recorder`는 수락·정지 시 각자의 활성 플래그를 영속한다(`FR-014`). 실제 가동 여부는 모니터링 스트림으로 확인한다(§3.3).

### (3) 이벤트 감지와 기록 (§6.6 (6))

재배포 스트림은 상시 흐르고, `recorder`는 이를 1초 세그먼트로 축적한다. 통지 이후의 클립 결합·이력 기록·용량 점검은 ***Event recorder*** 안에서 처리되며, 실패하더라도 ***Video analyzer***는 관여하지 않는다(§6.3).

### (4) 라이브 재생 (§6.6 (7))

HLS는 `Client app → router → streamer`의 중계 연쇄이고, WebRTC는 시그널링(WHEP)만 같은 연쇄를 거친 뒤 미디어가 `streamer → Client app`으로 직접 흐른다(§6.4). 두 경로 모두 인증은 ***Request router***에서 끝난다.

## 7.2 장면 분석 파이프라인 (Scene Analysis Pipeline)

처리 흐름과 시간 구조는 다음과 같다.

1. **프레임 추출** — GStreamer 파이프라인이 재배포 스트림을 디코딩하고 목표 주기로 정규화하여 링 버퍼에 쌓는다. 추출 주기와 링 크기는 설정값이다. 파이프라인이 (재)시작되면 링 버퍼는 초기화된다 — 추론은 현재 파이프라인이 추출한 프레임만 보며, 정지 전이나 프로필 교체 전의 프레임이 판정에 끼어들지 않는다.
2. **추론** — 워커가 링 버퍼의 최신 프레임 묶음과 프롬프트를 VLM 자식 프로세스에 전달한다. 추론 주기는 하드웨어 등급에 종속되며(SRS §5.4), 추론 중에도 프레임 추출은 계속되므로 다음 추론은 항상 최신 프레임에서 시작한다.
3. **판정** — 생성 텍스트에 이벤트 키워드가 대소문자 무시 부분 일치로 포함되면 이벤트다(`FR-029`). 키워드가 비어 있으면 매칭을 수행하지 않는다(`FR-027`).
4. **기록 개시** — 판정 즉시 ***Event recorder***에 통지하고 다음 추론으로 넘어간다. 이벤트 감지 지연(`NFR-004`)의 지배 항은 추론 주기이며, 통지·결합은 그에 비해 무시할 수 있다.
5. **클립 창의 기준점** — 클립 창(사전·사후 구간)은 판정 시각이 아니라 VLM이 본 마지막 프레임의 캡처 시각을 기준으로 자른다. 판정은 추론이 끝난 뒤에 내려지므로 실제 장면은 판정보다 추론 시간만큼 이전이며, 추론이 느린 하드웨어일수록 판정 기준의 창은 장면을 놓친다. 프레임 시각 기준은 추론 속도와 무관하게 장면을 창의 중심에 둔다. 이 차이가 실질적인 것은 수 초 안에 끝나는 순간 이벤트이며, 지속 상황에서는 쿨다운(`FR-030`)과 함께 어느 기준이든 결과가 비슷하다.

생성 토큰 상한은 설정값이다. 상한을 늘리면 장면 설명이 길어져 매칭 기회가 늘지만 추론 주기가 길어진다(SRS §5.4). 기본값은 프로토타입의 실측 균형(32)을 따른다.

## 7.3 상태 전이 (State Transitions)

분석의 상태는 `analyzer`가 소유하며 모니터링 스트림에 드러난다.

- **idle** — 활성 플래그가 거짓인 상태(기동 직후 또는 정지 후). 설정 저장(`/prompt`·`/camera`)은 이 상태를 바꾸지 않는다(`FR-025`).
- **waiting** — 시작 요청 접수 후 스트림 접속을 재시도 중인 상태(`FR-046`).
- **analyzing** — 프레임이 흐르고 추론이 도는 상태.
- **switching** — 모델 전환 중(`FR-032`). 자식 프로세스 교체 동안 분석이 중단되며, 완료 후 이전 상태로 복귀한다.

`/analysis/start`는 라이브 스트리밍이 진행 중인 한 모든 상태에서 유효하며 재시작으로 동작한다(`FR-024`·`FR-050`). idle로 돌아가는 경로는 분석 종료(`FR-051`)와 라이브 스트리밍 종료의 연쇄 정지(`FR-049`)이며, 정지 시 활성 플래그가 거짓으로 영속되어 재기동 후에도 idle이 유지된다(`FR-014`). idle에서 벗어나는 경로는 명시적 시작 요청뿐이다 — 워치독의 내부 재시작(§7.5)은 진행 중인 분석의 수복 수단이지 정지 상태를 뒤집는 경로가 아니므로, 정지와 겹치더라도 정지가 이긴다. 정지는 진행 중이던 판정도 폐기한다(`FR-051`) — 정지 이후에 완료된 추론은 상태에도, 이벤트 이력에도 나타나지 않는다. `recorder`의 버퍼 상태(off/buffering)는 분석 상태에 종속되어 같은 전이를 따른다(§2.4 (4)).

## 7.4 동시성과 자원 경합 (Concurrency and Resource Contention)

- **하드웨어 코덱** — NVDEC 디코드 세션은 상시 2개(`analyzer` 파이프라인, `recorder` 세그먼트 기록기)에 폴백 녹화 시 1개가 더해지고, NVENC 인코드 세션은 `recorder`의 1개뿐이다. Orin 계열의 코덱 처리량은 1080p 스트림 수 개를 감당하므로 경합보다는 세션 수 상한이 관건이며, 이 수치는 실측 항목(SRS §5)과 함께 확정한다.
- **통합 메모리** — VLM이 지배 항이다. 모델은 한 벌만 적재하고 전환은 반환 후 재적재로 직렬화한다(`NFR-023`). 나머지 상주 프로세스는 합쳐서 모델 대비 한 자릿수 아래에 머무는 것을 설계 전제로 하고, 위반 여부는 모니터링의 메모리 지표로 관찰한다.
- **프로세스 내부** — `analyzer`에서 추론과 프레임 추출과 요청 처리는 서로 다른 실행 단위에 있어 서로를 막지 않는다(§3.4). `recorder`에서 클립 결합은 통지 응답과 분리된 작업 스레드에서 돌며, 결합 중 새 통지는 쿨다운으로 걸러진다.
- **동시 스트리밍 세션과 추론의 상호 영향** — SRS §5.4의 실측 보류 항목이며 설계는 수치를 예단하지 않는다.

## 7.5 오류 처리와 복구 (Error Handling and Recovery)

원칙은 두 겹이다. 프로세스 안에서 수복 가능한 실패는 컴포넌트가 재시도로 수복하고, 수복 불능이면 종료하여 컨테이너 재시작 정책(`NFR-018`)에 맡긴다.

|실패|감지|대응|
|---|---|---|
|재배포 스트림 단절|`analyzer` 파이프라인 워치독 / `recorder` 세그먼트 생성 중단|파이프라인·기록기를 내부 재시작하고 접속을 재시도(`FR-046`)|
|`streamer` 컨테이너 재시작으로 소스 설정 소실|동반 프로세스의 기동 절차|스트리밍이 활성이었다면 적용 프로필을 스스로 재적용(`FR-015`)|
|VLM 추론 정지·실패|추론 워치독|자식 프로세스 재기동, 지속 실패 시 컨테이너 종료|
|이벤트 통지 실패|`analyzer`의 호출 오류|기록 포기(재전송 없음, §6.3). 지속 상황은 다음 추론이 재판정|
|세그먼트 결합 실패|결합 절차의 오류|직접 녹화 폴백(§4.4), 그마저 실패하면 상태 표시 후 포기|
|저장 공간 부족|기록 전 용량 점검|오래된 클립·이력 자동 삭제(`FR-033`)와 로그 기록(`NFR-010`), 확보 실패 시 기록 건너뜀과 상태 표시|
|내부 컴포넌트 무응답|`router`의 호출 실패|502 정규화(§6.5). 회복은 해당 컨테이너의 재시작 정책에 맡김|
|PTZ 불가(미지원·거부)|ONVIF 호출 실패|오류 없이 무시(`FR-020`)|

컨테이너 재시작이 복구 수단으로 성립하는 근거는 §4의 각 절이 밝힌 내부 상태의 성격이다 — 모든 컴포넌트가 재시작으로 잃는 것이 없거나(무상태·영속 상태), 잃어도 감수된 것(세그먼트 버퍼)뿐이다.
